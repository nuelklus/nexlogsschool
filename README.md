# NLSchool

NLSchool is a multitenant school-management SaaS. This repository is a fresh reconstruction from a partial recovery bundle, not a restored copy of the original repository.

## Structure

- `frontend/`: Next.js App Router application with TypeScript and Tailwind CSS.
- `backend/`: Django 5.2 LTS and Django REST Framework API, with academic management in the dedicated `academics/` app.
- `docs/recovery/`: preserved requirements, source transcript, and recovery notes.

## Recovered backend foundation

The initial Django app includes the recovered custom email-based user model and tenant, membership, campus, academic-year, subscription, invitation, email-action-token, and audit-event models. Initial migrations are included. The API exposes `GET /api/health/`, one-time initial school setup status and creation endpoints, staff invitation endpoints, and Django admin.

The recovered requirements specify invitation-only staff access, verified parent registration and student linking, student enrollment records independent of student login accounts, single-use expiring invitations or activation tokens, and backend-enforced tenant isolation and role permissions. The initial school setup page creates the first tenant and its owner membership; the owner must verify their email before signing in.

The recovery bundle did not include the original settings, API workflows, tests, or Next.js app. The current authentication endpoints are reconstructed; student/guardian relationship and enrollment models, academic management, finance ledgers/fees/invoices/payments, and school dashboards have since been implemented in this reconstruction. Finance supports tenant-scoped fee setup, bulk billing, double-entry postings, staff-recorded payments, receipts, statements, reports, and accounting-period controls. Online payment gateways and automated SMS/WhatsApp reminders are not configured; mobile-money payments require staff confirmation.

## Local setup

Use Node.js 22 or newer for the frontend. From this directory:

```sh
nvm use
cd frontend && npm install && npm run dev
```

In another terminal:

```sh
cd backend
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python manage.py migrate
python manage.py runserver
```

The frontend runs at `http://localhost:3000`; the API health endpoint is `http://localhost:8000/api/health/` and Django admin is at `http://localhost:8000/admin/`.

The backend loads `backend/.env` when Django starts; environment variables already set in the process take precedence. Keep that file private and out of source control. The project defaults to PostgreSQL when no database engine is configured. Set `DJANGO_DB_ENGINE` to `django.db.backends.sqlite3` to use SQLite, or configure `DJANGO_DB_ENGINE`, `DJANGO_DB_NAME`, `DJANGO_DB_USER`, `DJANGO_DB_PASSWORD`, `DJANGO_DB_HOST`, and `DJANGO_DB_PORT` for PostgreSQL. The PostgreSQL driver and `.env` loader are included in `backend/requirements.txt`.

## Staff invitations

An active school owner or school admin can create an invitation with `POST /api/tenants/{tenant_id}/invitations/`, using an authenticated API request and a JSON body such as `{"email":"staff@example.com","role":"teacher"}`. Roles are limited to `school_admin`, `accountant`, and `teacher`. The invitation email links to `/invitations/accept`; tokens are stored as hashes, expire after seven days, and are single-use. An authorized owner or school admin can revoke a pending invitation with `DELETE /api/tenants/{tenant_id}/invitations/{invitation_id}/`. Acceptance creates a verified staff account or adds the role to an existing account after the existing password is confirmed.

## Account authentication

All account types use the same email/password sign-in and JWT API. Sign-in returns a short-lived access token and an `HttpOnly` refresh-token cookie; refresh tokens rotate and are blacklisted on logout. Account flows:

- `POST /api/auth/login/` and `POST /api/auth/refresh/` issue and refresh the shared login session; `POST /api/auth/logout/` revokes its refresh token; `GET /api/auth/me/` returns the signed-in account's active school memberships.
- `POST /api/auth/email/verification-request/` sends a verification email; `POST /api/auth/email/verify/` consumes its single-use link. New owners receive this message during initial school setup.
- `POST /api/auth/password-reset/` requests a reset email; `POST /api/auth/password-reset/confirm/` consumes its single-use token, changes the password, and revokes existing refresh sessions.
- Frontend routes: `/login`, `/account/verify`, `/account/verification-request`, `/password-reset`, and `/password-reset/confirm`.

Staff, parents, and students all enter through single-use school invitations; there is no public registration.

## Enrollment, guardians, and student portal

All routes are under `/api/tenants/{tenant_id}/` and tenant-scoped. Owners and school admins manage; teachers and accountants can read.

- `GET/POST students/` and `GET/PATCH students/{id}/` — student records (unique admission number per school), independent of any login. Admission requires `initial_academic_year`, `initial_school_class` and `enrolled_on`, with optional `campus`; student and initial academic enrollment are created atomically. The year, class group and campus must belong to the same tenant, and the class group must belong to the selected year.
- `POST students/{id}/guardians/` (`email`, `relationship`, `is_primary`) — emails a parent invitation. A parent already in the school is linked to the additional child directly. `DELETE students/{id}/guardians/{link_id}/` unlinks.
- `POST students/{id}/portal-invitation/` (`email`) — invites the student to activate one portal account.
- `GET me/children/` (parent) and `GET me/student/` (student) — a parent sees only linked children; a student sees only their own record.

Invitations are accepted at `/invitations/accept` and can be revoked with the existing invitation `DELETE` route.

The frontend page `/school` uses these routes by role: owners and school admins enroll students and send guardian or portal invitations, teachers and accountants get a read-only list, parents see their linked children, and students see their own profile. Run the frontend checks with Node 22 (`npm run lint`, `npx tsc --noEmit`, `npm test`, `npm run build`).

## Academic management

The **Overview → Class levels & classes** setup lets school owners and administrators select Ghanaian catalogue levels or create school-specific levels, rename them locally, reorder them and archive or reactivate them. Platform staff with Django admin permissions maintain the global catalogue. Existing classes are not mapped automatically. Academic Management retains class and level views; use Overview for setup.

Admission loads active academic years and class groups from the tenant's academic APIs and records the selected group as the student's initial enrollment. The displayed current grade is derived from the single active enrollment in the current academic year; the legacy student grade remains a compatibility fallback when there is no unambiguous current enrollment.

The tenant APIs are `GET academics/class-level-catalogue/`, `GET/POST academics/class-levels/` and `PATCH academics/class-levels/{id}/`. No delete endpoint is provided; archive a level by setting `is_active` to `false`. Schema migration `0005` adds two tables and `0006` seeds the Ghana catalogue without modifying school records. Rolling back `0006` leaves seeded entries in place; rolling back `0005` after schools configure levels would destroy that configuration and must not be used as a data-preserving rollback.

Administrators can explicitly assign a configured level to existing classes in Overview's class setup, or use `PATCH academics/classes/{id}/level/` with `{"class_level":"<level UUID>"}` (or `null` to clear it). The class creation API accepts an optional `class_level` and requires an active `campus`. Existing classes are not mapped automatically; archived levels retain their links but cannot be newly assigned. New fee schedules may target a configured class level, and billing matches them through the student's enrollment for the selected period. Legacy text-based fee schedules remain supported. No existing fee schedule is automatically mapped and no issued invoice or financial posting is recalculated when a class or level changes.

Migration `finance.0008` adds a nullable protected class-level reference to fee schedules while retaining the legacy text field. Existing schedules are not mapped automatically; configure new class-level schedules only after verifying the school's class-level assignments.

Owners and school administrators can create and manage campuses in **Overview → Campuses**. Create at least one active campus before creating classes, even for a single-campus school. Campus deactivation preserves existing records. No existing class or enrollment is automatically assigned a campus.

The **Students** roster can be searched by name, admission number or grade and filtered by current-year class group, campus, status, gender and portal access. Class-group filtering uses the student's unique active enrollment in the current academic year; students with no such enrollment or multiple active enrollments appear under **No unique current class**. Campus uses enrollment evidence where available, with a profile fallback. These filters do not change student records.

Select a student's name in the roster to open a read-only details dialog with their profile, current-year class, account summary and most recently created non-void invoice. The latest invoice may not belong to the current term. Outstanding invoice balances and unallocated advance credit are shown separately; draft invoices are not yet outstanding. Financial details use the existing finance permissions and are loaded when the dialog opens.

When creating a class under **Overview → Class levels & classes → Classes**, select an active campus and class level. A single active campus is preselected; with multiple campuses, choose one explicitly. Campus is required by the class-creation API as well as the interface, so older API clients must supply it. The campus cannot be changed after enrollment, and an assigned campus cannot be cleared. The class name can be edited and section and room are optional. Schools can also explicitly choose “No level (assign later)” for an unmapped class. Selecting a level does not change existing student enrollments or fee schedules. Historic missing campus evidence still requires separate reconciliation; this setup does not repair it.

Class name and section must currently be unique within an academic year, even across campuses. Use distinct class names or sections until campus-aware class naming is designed.

The class setup also provides a read-only reconciliation report (`GET academics/class-reconciliation/`, owner/admin only). It lists unmapped classes with possible configured-level matches and flags active students with missing, conflicting or multiple current-year enrollments. Suggestions are not assignments; staff must verify and assign levels themselves. No current year means student checks cannot run. Historical records and fee schedules are not reconciled by this report.

The Academic Management workspace is available at `/academics` to owners, school admins, accountants, teachers, and headteachers. Owners and school admins set academic years and terms manually in Overview; no terms are generated automatically. They also manage classes, subjects, teacher assignments, student class/subject enrollment, timetables, and assessments. Staff can review academic records; teachers can record attendance and assessment results for classes and subjects assigned to them. The tenant-scoped API is under `/api/tenants/{tenant_id}/academics/` and includes collections for years, terms, classes, subjects, teacher assignments, enrollments, attendance, timetables, assessments, and results. At year end, the Promotion tab uses `/academics/promotion/`. Schools may mark one active class level as terminal; graduation is suggested only for classes explicitly assigned to that level. Mapped levels use school sort order for next-level suggestions, and ambiguous destinations are left for staff to select. Unmapped classes retain legacy name-based progression but are not automatically suggested for graduation. The target year must start after the source year ends. Administrators may override suggestions.

In **Promotion**, select the source year, target year and source class, then load and review that class's students before applying their decisions. Repeat for each class. Bulk actions affect only the loaded class. Making the target year current is optional and unchecked by default because it affects the whole school; select it only when ready to change the current year and billing class information. If the destination year is already current, applying placements updates billing class information even with the box unchecked. The promotion preview API continues to support school-wide previews when `source_class` is omitted.

In **Academic Management → Exams & results**, owners and administrators can create grading configurations and individual managed examinations, or create an examination session with multiple class/subject entries. Each entry has its own grading configuration, schedule and independent workflow. A session creates new exams; it does not add existing individual examinations, so leave previously created subjects out unless another exam is intended. Use **Load session progress** to refresh counts; teachers see only their assigned entries and counts, while leaders see school-wide entries. Session creation is atomic and rejects duplicate class/subject pairs. Session schedule editing and bulk workflow actions are not yet available.

The **Created examinations** list includes individual examinations and session entries accessible to the signed-in user; use **Refresh examinations** to reload it and the term, class and status filters to narrow it. **Open** moves focus to the examination details. Save unsaved draft marks before opening another examination. Create one examination per class and subject, not per student: its roster comes from eligible enrollments on the examination start date.

For official report cards, publish each required subject result first. A headteacher reviews each report, then an owner or administrator loads and publishes the reviewed reports. Loading the report list shows accessible reports across the school, not just the open examination. A class ZIP does not create reports: every student on the selected dated roster must already have a published report. If batch review reports that a reviewed version awaits publication, publish that version rather than reviewing it again.

Under **Saved grading configurations**, expand a configuration to see its components, grade bands and calculation settings. Owners and administrators can edit its latest version; saving creates a new version, while previous versions and existing examinations remain unchanged. Choose the desired version when creating an examination.

The assigned teacher saves draft marks and submits the saved marks after the examination ends; a headteacher reviews and approves or returns them with a reason; an owner or administrator publishes manually on or after the publication date. Teachers can see and mark only their assigned class and subject; leaders have school-wide access. Parents and students see only their own published result snapshots in the school portal. The marks deadline is informational, not an automatic lock.

The class roster is based on the examination start date and the student's enrollment subjects, treating an empty subject list as all class subjects. Missing and absent marks block finalization; exempt components are excluded and remaining weights rescaled. The school explicitly chooses whether not-applicable components are excluded or block calculation. Zero is a scored mark, not an absence. Scores, configuration and context are checked for changes between submission and publication; return and resubmit if they change. Publication preserves snapshots and does not change legacy results or financial records. The prior assessment forms remain available as legacy functionality and their results are not published through this workflow.

For a published correction, an owner or administrator starts a new version with a reason. The previously published version remains visible to parents and students while the teacher edits and resubmits; a headteacher must approve and an administrator must publish again. The new publication replaces the visible version, but previous snapshots and mark audit events remain in history.

Owners and administrators can also use `POST academics/grading-configurations/` and create a new immutable version with `POST academics/grading-configurations/{id}/revisions/`; academic staff can list versions. Each revision requires the complete configuration and can only be made from the latest version. Component weights must total 100 and grade bands must include zero. Migration `academics.0013` adds the configuration table without mapping or altering historical results. Migration `academics.0014` adds examinations and publication snapshots and extends existing assessments/results; it marks existing results as scored without recalculating them. Reversing `0014` removes managed examination data and may fail if unscored marks exist; do not treat it as a data-preserving rollback.

Migration `academics.0015` versions publication snapshots and backfills existing publications to version 1 without changing their content. Reversal is not data-preserving and may fail once later versions exist.

Migration `academics.0016` adds examination sessions and an optional session link to examinations without changing existing results. It has been applied to the local development PostgreSQL database; reversing it removes session data and links.

Migration `academics.0017` adds versioned report-card records without changing historical marks or examination publications. It has been applied to local development PostgreSQL. Reversing it deletes report-card history and is not a data-preserving rollback.

Transfer reporting decision and data limitation: the chosen policy is a **separate report for each enrollment segment**, using only that segment's results and attendance; incomplete or ambiguous history must block review. The current enrollment-subject many-to-many relation and fallback teaching assignments do not record historical effective dates or an attestation, while older enrollment campus references can be null and class campus can be changed. Consequently neither can establish all historically applicable subjects or a missing campus without guessing. The present report schema also numbers versions per student and term, rather than per segment, and its reviewed-version guard applies across the whole term. Existing published examination snapshots are tied to an enrollment but do not establish the complete historical subject roster. Within-term transfer review therefore remains blocked.

**Attestation revocation:** owners and school administrators may revoke an individual attestation with `POST academics/enrollment-provenance/<attestation_id>/revoke/` and a nonblank `reason`; the reconciliation screen provides a reason and explicit confirmation for the latest version, and shows revocation details in its history. Each attestation can be revoked once. A separate protected record stores actor, timestamp and reason, and the action and version are audited in the same transaction. An authorized user can make a new attestation version, including the same verified values, after revocation; the old attestation and revocation remain in history. Revoked attestations fail the read-only segment inspection. Published reports are not rewritten or automatically withdrawn, and remain accessible as before; staff must investigate and use the existing audited revision process when correction is required. There is no automatic parent notification or downstream incident workflow. There is no supported API to delete or undo a revocation; direct database/admin writes are outside this guarantee.

**Provenance inspection groundwork (not enabled):** `backend/academics/report_provenance.py` reads the term/year, student, enrollment and overlapping enrollment history, classes and campuses, enrollment subjects and class teaching assignments, latest attestation and revocation, subjects, selected examinations and sessions, examination publications/snapshots, assessments, marks and segment attendance. It checks tenant, year, term, enrollment, class, subject, dates, status/score shape and exact latest non-revoked attestation relationships, including grading configuration tenant. Published component marks must match current component status, numeric score and remarks; malformed scores, duplicate component keys and inconsistent attendance are rejected. This is intentionally conservative: a correction in progress can make current marks differ from the still-visible published snapshot, and older snapshots lacking mark remarks need reconciliation rather than an invented value. The attestation's evidence is a human assertion, not a historically dated assignment record; missing campus and assignment history cannot be independently inferred. It assumes one selected published examination per attested subject, that full examination dates fit the segment and that current components/marks exist; these conservative assumptions may block valid historic cases. Its digest includes attestation details, publication/mark/assessment identities, examination version/configuration, presentation names and segment attendance as well as result snapshots. It does not recompute the published subject grade from the saved grading configuration or prove a consistent snapshot. The existing `_context` fingerprint includes enrollment marks and publications across all periods, so unrelated changes can require a new attestation. Inspection makes multiple reads without a coordinated snapshot and can become stale even before it returns. It remains read-only and is not connected to preview, review, publication, class review or export; it supplies no concurrency guarantee.

**Locking status:** no safe common publication lock strategy has been implemented. Revocation locks term then attestation, and attestation creation locks term then student then enrollment; simultaneous revocations serialize on the term and a uniqueness constraint permits only one revocation. Linked report publication is deliberately blocked, regardless of revocation, rather than purporting to validate it. Managed examination mark/action writes now lock the term before the examination, matching the term-first portion of individual/class review and transfers; authorization is checked again after locking. Publication locks report then term; transfers lock ordered terms then student, enrollment and target class. Class/campus, teaching-assignment and other write paths do not all take the same coordination locks. Row-locking only currently existing rows would not prevent newly inserted enrollments or assignments. A common order and parent/coordination locks must be enforced across every relevant writer, including phantom inserts, before this inspector can be used as a publication safeguard. No class-wide publication endpoint exists. Existing unlinked report review/publication still use legacy checks, which do not fully detect subject, attendance, campus and mark changes.

### Focused email verification / invitation deadlock investigation

**Decision: Stage 2A remains NOT READY.** The actual views reproduce a deadlock in a deliberately controlled schedule on a disposable, model-built PostgreSQL schema. This is not evidence that it occurred in production. No remedy or application behavior change was implemented.

**Cycle and evidence.** The fixture contains an unverified shared user with an active membership and an invitation for the same tenant. Here *obsolete* means the invitation is still unexpired, unrevoked and unaccepted, but the membership already exists; it does not mean expired. Requests are dispatched to the actual DRF view classes on independent PostgreSQL connections, without HTTP middleware.

1. Verification validates input before `transaction.atomic()`. Inside, `get_email_action(..., lock=True)` executes a token/user join `SELECT ... FOR UPDATE` with no `OF` restriction, locking the matching `core_emailactiontoken` and joined `core_user` rows. The test pauses immediately afterward.
2. Acceptance hashes its token and captures `now` before its atomic block. It executes an invitation/tenant join `SELECT ... FOR UPDATE`, with no `OF` restriction, and holds the matching `core_membershipinvitation` and joined `core_tenant` rows. SQL does not guarantee their acquisition order within this join. After checking invitation state and tenant status, this teacher invitation requests `core_user SELECT ... FOR UPDATE` by email. `pg_blocking_pids()` and the active SQL show acceptance waiting for verification on this query.
3. Verification resumes, updates `core_user.email_verified`, reads active `core_membership` tenant IDs, inserts tenant-scoped `core_auditevent` rows, and updates `core_emailactiontoken.used_at`. In the test schema the audit-to-tenant FK is confirmed `DEFERRABLE INITIALLY DEFERRED`. Its commit-time parent check requires a tenant `FOR KEY SHARE`, incompatible with acceptance's tenant `FOR UPDATE`.
4. The resulting graph is acceptance holding invitation/tenant → waiting for user held by verification; verification holding user/token → waiting for tenant held by acceptance. PostgreSQL's `40P01` detail identifies both reciprocal process/transaction-ID `ShareLock` waits. In the two final runs the victim context identified the `core_user` tuple; a tenant-side FK query was **not directly captured in those deadlock contexts**. Separately, a diagnostic transaction holding that tenant row caused the real verification view to wait at `COMMIT` after its audit insert; together with the verified deferred FK and SQL trace, this supports the tenant-FK explanation. The separate holder is a test-only probe, not another business workflow. Granted `RowShareLock` entries observed for invitation and tenant are relation-level locks, not themselves tuple-lock evidence. PostgreSQL may also take internal transaction, index and FK locks.

When acceptance is the victim verification returns 200; if verification is the victim acceptance returns 409. The obsolete invitation remains unaccepted; verification state and token usage agree after commit or rollback. The traced obsolete acceptance reaches the membership check only after locking user and tenant, and returns 409 before password checks, user or membership updates, invitation acceptance, or acceptance audit insertion. The teacher case does not lock a student; parent/student invitations can also lock `core_student` and write guardian/student records. Existing user email and both token hashes are unique; `(tenant, user)` membership uniqueness and the invitation, token, membership and audit FKs enforce integrity but are not a general ordering protocol. The joined-lock queries and deferred parent checks are important implicit parts of the graph; exact internal row-acquisition order and all PostgreSQL internal SQL are not captured.

Invitation issuance checks for current pending invitations; expiration itself is a time/state check, not an automatic expiration write.

### Stage 2A disposable PostgreSQL fixture strategy

**Status:** the fixture mechanism is demonstrated, not the Stage 2A lock architecture. Stage 2A is **NOT READY**; transfer-aware issuance remains blocked. No admission, finance, subscription, closure or shared-user race suite was started as part of this fixture task.

### Cross-module deadlock resolution design (for review; not implemented)

**Decision and scope.** Recommend one tenant-scoped PostgreSQL transaction advisory coordinator, acquired on the primary connection before *any* relevant database read, row lock, insert, update, uniqueness wait or potentially writing authorization check, combined with a common row-lock order below. Use the existing Stage 1 service, not a second independent coordinator. The order in this section supersedes the earlier proposal below where they differ; both are design targets, not implemented behavior. This is a proposed all-participant protocol, not an assurance of a deadlock-free deployment. Finance, admissions, academic management, reporting, authorization/subscription and maintenance paths that may enter the same wait graph must be refactored and tested together or fenced; a partial release is not safe. This design does not implement Stage 2A or change existing behavior.

**The reproduced wait cycle.** In `test_stage2a_lock_conflict.py`, transaction A simulates a *proposed*, not current, admission order: acquire the advisory coordinator, then lock the tenant `FOR UPDATE`, then request the current year `FOR UPDATE`. Transaction B simulates the current finance year-create sequence and does not acquire the coordinator: update the current year to `is_current=false`, insert a new year, then commit. B holds the old year row while A waits for it; the new year's deferred tenant FK check at commit requires a key-share lock on the tenant, conflicting with A's `FOR UPDATE`, so B waits for A. PostgreSQL's deadlock detector aborts one transaction with `40P01`. The earlier isolated test observed A's blocking via `pg_blocking_pids()` and the deadlock SQLSTATE; it did **not** capture the full server deadlock graph, so the precise commit-time wait should also be asserted in a future diagnostic test. If the FK is immediate, the same parent check can wait during the insert rather than commit; deferred checks can make the wait appear after application logic finishes. The reproduction is not evidence that a production deadlock occurred, or that current admission itself uses this proposed order.

The current admission path actually locks **year → class → tenant**, then creates/updates admission settings and sequence, inserts student/enrollment and audit rows. The tenant lock protects first sequence creation, and unique `(tenant, period)` and `(tenant, admission_number)` indexes provide final database enforcement; their checks can wait on another transaction and must not be discarded. A profile override or uncoordinated SQL can still conflict, and sequence rollback must be tested. These are facts about that test schema, not a production schema certification. The partial unique indexes for one current year and one current term, unique enrollment/student-class, assignment and admission-number constraints can wait on competing index entries; they are integrity backstops, not a lock-order protocol. A non-deferrable FK or a constraint explicitly set immediate may instead check earlier. Inserts, deletes, parent-key changes, cascades, database triggers, and Django many-to-many through writes may introduce further locks. No application signal receiver was found in the repository search; deployed plugins, database triggers and external jobs remain unverified. Django's `on_delete` behavior and actual database FK actions must both be inspected rather than assumed.

### Stage 1: academic coordination lock foundation

`backend/academics/coordination.py` provides `acquire_academic_coordination(tenant_id, using="default")`. It accepts a nonzero tenant UUID or UUID string, not a tenant object; it checks syntax, not whether the tenant exists. It requires PostgreSQL, a Django-managed outer `transaction.atomic()` and `READ COMMITTED`, and uses the named connection for both the lock and the caller's work. Unsupported backends, missing or invalid IDs, calls outside an appropriate transaction, other isolation levels and attempts to coordinate a second tenant in one transaction fail explicitly.

The key is the first eight bytes of SHA-256 over the versioned byte namespace `nlschool.academic-coordination.v1\0` followed by the canonical 16 UUID bytes, interpreted as a signed big-endian 64-bit integer. Reserve the application's single-bigint advisory-lock namespace for this protocol. A 128-bit UUID cannot be mapped injectively to 64 bits: a collision can unnecessarily serialize unrelated tenants, but must never grant access to data. Locks do not authorize users or verify tenancy. Do not change the namespace or key algorithm while processes using this protocol are running.

Required pattern for future participants, on the **primary** database and the same alias throughout:

```python
from django.db import transaction
from academics.coordination import acquire_academic_coordination

with transaction.atomic(using="default"):
    acquire_academic_coordination(tenant_id, using="default")
    # Authorize the actor and verify the tenant and scope.
    # Read and validate current sources, then take required row locks in order.
    # Perform the operation and commit when the block exits.
```

Start a fresh outer `READ COMMITTED` transaction, acquire the coordination lock before relevant source reads or row locks, perform authorization and tenant-scope checks, read and validate the sources, acquire necessary row locks in the proposed hierarchy below, perform the operation, and commit. Source reads and tenant-dependent authorization must not be trusted if performed before the lock. The service cannot detect earlier reads, wrong aliases or nonparticipating writers; these remain caller and deployment responsibilities. Lock timeouts and retryable error handling remain future integration work.

The service calls PostgreSQL `pg_advisory_xact_lock`, not a session lock. PostgreSQL releases it on commit, rollback or connection loss. Repeated calls for the same tenant in the same transaction, including within a nested Django `atomic()` block, are safe. PostgreSQL releases a lock first acquired after a savepoint if that savepoint is rolled back, so the service rejects the first acquisition inside a Django-managed savepoint. A nested `atomic(savepoint=False)` is allowed before the first acquisition because it creates no savepoint. The service tracks the backend PID, transaction ID and tenant on the Django connection to recognize reentry; state from an earlier transaction or connection is not reused. Only Django-managed `atomic()` savepoints are supported: do not create manual `transaction.savepoint()` or SQL savepoints, change autocommit, commit, roll back, or switch connections behind the service. In particular it cannot detect an unmanaged savepoint created before the first acquisition. Acquire at the start of the outermost block, and do not assume any lock survives a rollback of the transaction that acquired it.

The intended additional row-lock order is tenant/admission settings/sequence/user/membership; academic year; term; campus/class level/class/subject/teaching assignment; student/enrollment/enrollment-subject rows; examination session/examination/configuration/assessment/mark; attendance/attestation/revocation; report/closure/workflow. Sort IDs within each model and audit implicit foreign-key and joined locks. This is a future contract, not the current behavior. The service permits only one tenant per transaction; multi-tenant work requires a separately designed and tested protocol.

### Proposed academic data protection architecture (broader design; not implemented)

**Status and boundary.** This is a proposed replacement for the incomplete protection described above, not a claim that the current APIs use it. Transfer-aware issuance and publication of linked reviews remain blocked. Current unlinked publication remains available but is not fully protected; the proposed cutover would deliberately block it until the policy below is implemented. The school policy remains one report per enrollment segment, with no merging of marks or attendance across segments. The current enrollment-subject and teaching assignments have no effective-date history; a verified attestation is evidence supplied by an authorized person, not independently reconstructed history. Current `_context` also includes other-period sources, and the inspector does not recompute the published subject grade. Both require explicit compatibility work.

**Coordinator choice and alternatives.** Use a PostgreSQL *transaction-scoped exclusive advisory lock per tenant* as the first coordination lock for every participating transaction. Derive a stable signed 64-bit key from a documented versioned application namespace and the canonical tenant UUID using a fixed cryptographic digest, never Python's randomized `hash()`. Reserve that advisory-lock key space across this application. Hash collisions must cause only unnecessary serialization, never shared data access; log and investigate suspected collisions. Locks are not authorization. PostgreSQL releases the lock on transaction completion or connection loss; use the transaction-scoped, not session-scoped, API on the same connection as all reads and writes. This works only if every relevant writer participates or is fenced. It serializes unrelated academic work within one tenant, including long class batches; benchmark contention and set operational limits before considering finer granularity.

Alternatives: existing-row locks cannot protect missing enrollments, assignments or revocations from concurrent inserts without a shared parent lock; locking the tenant row first would conflict with current admission's year/class-before-tenant order and affects other subsystems. A new per-tenant coordination row gives exact tenant keys and inspectable locks but needs an additive table/provisioning and all writers still need to acquire it first; it is a viable fallback if collision-free lock identity is required. Serializable isolation can detect some anomalies but requires whole-transaction retries, is not a substitute for coordinating all writers and lacks an agreed rollout for existing workflows; a digest or timestamp alone cannot prevent races. A trigger that acquires an advisory lock *after* a statement has already acquired row locks can invert the order and deadlock; do not treat such a trigger as the coordinator.

**Transaction and lock order.** Use a fresh outermost `READ COMMITTED` transaction on the primary database. Before any database-derived validation, source read, row lock or write in that transaction, acquire the tenant coordinator; pre-lock request syntax parsing is permitted but ORM instances, permissions and derived values must be fetched and validated again afterwards. Do not enter through an outer transaction that already holds relevant locks. In particular, do not use `REPEATABLE READ` with the advisory-lock `SELECT` as the first snapshot: a waiter can retain a snapshot from *before* the lock was granted. Under `READ COMMITTED`, each subsequent source read starts after the barrier and all participating writers remain blocked until commit. Acquire no new tenant coordinator after row locks; a future multi-tenant operation must determine all tenants first and lock their coordinator keys in deterministic sorted order before any rows, or be prohibited.

After coordination, acquire only the necessary explicit row locks in this proposed order, with IDs sorted within each named model: (1) tenant, admission settings, admission sequence, user and membership; (2) academic year, then term; (3) campus, class level, class, subject and teaching assignment; (4) student, enrollment and enrollment-subject through rows; (5) examination session, examination, grading configuration, assessment and mark; (6) attendance, attestation and revocation; (7) report version, then closure and other workflow rows. Writes to multiple terms, students or reports precompute and lock all applicable IDs in order, and newly discovered earlier-order rows require a restart rather than an order inversion. Shared global-user operations affecting multiple tenants must predeclare and coordinate all affected tenants in sorted order or use a separately proven safe protocol. This is a target ordering, not a property of the present code: reconcile admission numbering, promotion, closure, report publication/withdrawal and cross-feature paths before enabling it. Avoid implicit joined `FOR UPDATE` locks (`of=('self',)` where supported); account for PostgreSQL foreign-key key-share locks, uniqueness checks and audit/finance rows when verifying the complete wait graph. All code that may take a shared row and later request the coordinator must be refactored or fenced; a coarse advisory lock cannot prevent deadlocks involving nonparticipating subsystems or shared global records.

Use bounded lock/statement timeouts and translate lock timeout, deadlock (`40P01`) and serialization (`40001`) into explicit retryable errors without leaking other tenants' data. Where retry is appropriate, roll back and rerun the *entire* transaction with bounded retries; never retry inside a broken transaction. Use request idempotency and a durable outcome for ambiguous commit/retry cases. Do not hold the lock over network calls or PDF/ZIP rendering. Record structured wait duration, timeout/deadlock counts and audit outcomes without logging student evidence or marks. Lock acquisition, read-after-wait, implicit locks, supported connection pooling and rollback behavior must be verified, not assumed.

Inventory completeness, foreign-key cascades, global user changes, cross-tenant references and every SQL role/job must be verified against the deployed environment. The intended operational fence gives only coordinated application services the protected-table DML credential, blocks direct access to that credential, and revokes source-table write privileges from interactive, integration, old-release and uncoordinated job roles. This controls those roles, not arbitrary SQL issued using the application credential itself. If the deployment cannot enforce that trust boundary, a stronger separately designed database API is required: revoke protected-table DML from the runtime role and allow only hardened, tenant-authorized procedures that acquire the coordinator before touching any source row. Such a database API would be a substantial architectural change and needs its own security and lock-order review. Privileged break-glass writes require an exclusive maintenance fence and audit. Where actor membership or source fields can change without joining the coordinator, the proposed consistency and authorization guarantee does not hold.

**Authoritative validation and evidence contract.** Implement one side-effect-free *validation and construction function* callable only inside the coordinated outer transaction, returning immutable typed evidence and the exact report presentation snapshot; callers own the atomic persistence and audit. It must fetch current records after the barrier and reject rather than infer. Validate: tenant and current actor authorization; term/year and one exact enrollment/student/class, segment bounds and status; all potentially overlapping enrollments (different consecutive segments are permitted, actual overlap, unexplained gaps or conflicting ownership block); latest explicitly selected attestation ID/version, evidence, original-context compatibility, dates, tenant campus or explicit verified no-campus, and absence of revocation; the attested subject set and documented valid assignment evidence; one explicit published examination per required subject, matching session, term, class, enrollment and segment dates; publication identity/version, component definitions and all current marks/statuses against the publication. Recalculate and compare score, grade and description using the publication's verified configuration and exact existing grading rules; if older snapshots lack sufficient evidence, block reconciliation rather than fabricate it. Explicit zero remains a score; missing/absent block, exemption and not-applicable follow the recorded policy. Validate segment attendance, statuses, ownership, dates and duplicates. Current campus or teaching assignments are context, not proof of historical values; a current class-campus change alone must not replace an attested historical campus.

Construct a versioned canonical evidence document containing tenant, student, term/year, enrollment ID and segment bounds, class and attested campus identities and display values, exact attestation ID/version and evidence reference, attested subjects and supporting assignment identities, examination/session/date/configuration identities and values, selected publication IDs/versions and immutable result snapshots, component and mark IDs/status/scores/remarks, attendance IDs/dates/statuses and totals, all presentation inputs and calculation-policy/version. Canonicalization specifies deterministic sorting, UUID/date encodings, decimal strings, null semantics and schema/algorithm versions; hash its canonical bytes with SHA-256. Include all conflict-detection inputs, including other relevant enrollments, and document why a source field is included or excluded. Keep sensitive attestation evidence in protected staff-only storage, not a parent-visible snapshot or client token. Store exact identities and values, not just a hash, in an append-only, access-controlled report evidence record; retain the existing immutable report rendering snapshot and actor/time/audit history. Proposed additive nullable evidence/schema/digest storage and protected attestation linkage require a new migration after `0020`, no backfill or rewriting of historical reports, and explicit immutability enforcement. A hash is a change detector, not proof of historical correctness.

The existing attestation `source_fingerprint` format must not be silently reinterpreted. Define versioned verification for existing attestations and a separate, narrowly scoped evidence format for future attestations; if an old fingerprint cannot be checked safely, require an authorized new attestation rather than rewriting the old one. A later attestation, even with identical values, or any revocation invalidates an outstanding review until a new explicit review; never silently switch the linked version.

**Workflow.** Preview acquires the coordinator, runs the same complete validator, builds the snapshot and returns a short-lived authenticated, tenant/actor/purpose-bound token containing only a digest, evidence schema/version, selection and expiry (or a server-side opaque identifier). It is not an authorization grant. An incomplete exploratory preview, if retained, must be visibly unofficial and cannot supply a review token. Individual review rechecks the token, actor and every source inside a new coordinated transaction; a mismatch returns a clear reload/reconcile error. It binds the exact attestation and evidence and creates a reviewed version and audit event atomically. Class review reselects and validates the dated roster after acquiring the same lock, requires one explicit token/selection per segment, invokes the identical individual validator for each row and commits all or none, preserving per-row errors.

Individual publication acquires the coordinator before locking the report, reruns the same source validator against the *stored* segment, selected publications and attestation, and compares the new evidence digest and the stored report/snapshot integrity digest to the review values before changing status and auditing in the same transaction. Stale, revoked, superseded or malformed evidence fails with a recoverable withdraw/review instruction. Do not update the existing reviewed evidence to make it pass. A future class-publication API must authorize the administrator, reselect the dated roster under the lock, call the identical individual publication validation for every report, and either commit all or none with per-student errors; there is no such endpoint today. Audits include action, actor, report/segment/attestation IDs and versions, digest/schema, and reason where required, without exposing evidence to unauthorized users.

Maintain the existing unique student/term version sequence; under coordination, allocate the next version deterministically. Change the reviewed guard to `(term, enrollment)` so independent segments can be reviewed separately, with a database partial uniqueness constraint where feasible. A first issue for another segment is not a correction; a subsequent issue of the same segment needs a reason. Keep prior versions and their term-wide numbers. The roster and ZIP export must select by historical enrollment and date, fail on overlapping eligibility or missing reports, and use that segment's latest published version; previously issued versions remain accessible. Rendering uses copied published snapshots, not live sources, and successful export auditing must not claim success if rendering fails.

**Historical and revocation policy.** Existing published reports remain byte-for-byte unchanged in stored snapshot, linked or unlinked, and accessible through existing authorized retrieval; regenerated PDFs are not guaranteed byte-identical. Do not backfill attestation IDs, mark existing reports verified, infer missing campuses/subjects, or rewrite marks. At cutover, previously reviewed unlinked versions and reviews missing a complete supported evidence digest are **not publishable**: offer an audited withdrawal and a new preview/review after authorized evidence-backed reconciliation. Do not mutate their snapshot or manufacture a token. Revocation or supersession blocks new review/publication immediately; it does not silently withdraw or alter a published report. Raise an auditable staff investigation with affected report IDs and use an explicitly authorized correction/revision; notification or withdrawal policy is separate and not yet implemented. Unattested, missing, ambiguous or genuinely overlapping histories remain blocked. The prior local observation of three missing-campus segments is historical, not a fresh audit.

```json
}
```

`class_level` may be an active level ID from the same school or `null` for an unspecified level. Rounding accepts `half_up`, `half_even`, or `down`. Configurations have no editing or deletion API; an administrator submits a full replacement as a new revision. Rolling back migration `0013` deletes all grading configurations, so it is not a data-preserving rollback.

Headteachers can read their school's student list and profiles as well as academic records, including the timetable and attendance history. The headteacher role cannot admit or edit students, create timetable lessons, or record attendance. Their term-closure academic approval remains distinct from owner/admin final authorization.

On the **Attendance** tab, attendance history can be filtered by student, academic year, class, date range and status; totals reflect those filters and include matching records from past enrollments. To record a class register, select its year, class and date, choose a status for each student without a record, and save. Already recorded entries are displayed but never overwritten. Teachers can submit registers only for assigned classes. The `POST academics/attendance/register/` endpoint accepts `school_class`, `date` and an `entries` list of `enrollment`, `status` and optional `notes`. It validates each enrollment against the selected class and date and saves the batch atomically. A concurrent duplicate returns a conflict without saving the batch; reload the register before retrying. Completed terms cannot receive register entries until reopened.

Migration `0008` adds a terminal-level flag and uniqueness/check constraints. It defaults existing levels to non-terminal and does not change students. Rolling it back removes terminal settings, so record the configuration before reversal.

The finance dashboard's class and campus collection breakdowns use the class and campus recorded on each allocated invoice, not the student's current details. Unallocated and refunded-from-unallocated amounts for the selected payment period are reported separately. Money Received class and campus filters include only amounts allocated to matching invoice snapshots, not advances or refunds. The breakdown reflects allocations and refunds as they stand now, so allocating an advance later changes the historical breakdown; the unfiltered payment-date total remains gross confirmed receipts. Invoice snapshots are only as accurate as the information recorded when each invoice was created, and a deleted campus cannot be recovered from its nullable reference.

Owners and administrators can assign an active school teacher as class teacher, set a class group's campus, and archive or reactivate existing classes in Overview's class setup, or use `PATCH academics/classes/{id}/management/` with `class_teacher`, `campus` and/or `is_active`. Archived classes remain visible with their enrollment and history, but cannot receive new enrollments, transfers or promotions. Archiving does not change current student grades or finance. Migration `0010` adds the optional teacher and active flag, defaulting existing classes to active. Migrations `0011` and `0012` add nullable campus references to class groups and enrollments; existing records are not assigned a campus automatically. Reversing migrations removes their respective class, enrollment or teacher settings; export and reconcile these before rolling back.

Owners and school admins can transfer an active student between classes in the current academic year from the Enrollment tab or with `POST academics/transfers/`. The source enrollment and its attendance and results remain in place; its end date is the day before the transfer, and a new enrollment starts on the effective date. Transfers require a reason and cannot be future-dated, affect a closed term, or precede existing source-class attendance or results. A destination class at a different campus is rejected; returning to a previously attended class is not yet supported. New billing resolves class and campus using the enrollment that covers the selected term's start, and snapshots that context on the invoice. If no term matches, the academic-year start is used with a warning; if no enrollment covers that date, legacy profile class and campus are used with a warning. Existing invoices, payments, allocations and posted journal entries are not reassigned or recalculated.

Migration `0009` adds a nullable enrollment end date, a transferred status and an ordered-dates constraint. Existing enrollment IDs and references are unchanged. Reversing the migration removes end dates and older application versions may not understand the transferred status; preserve transfer history and plan a compatible application rollback before reversing it.

## School finance

Finance screens are under `/finance` and are available to school owners, school admins, and accountants. The tenant-scoped API is under `/api/tenants/{tenant_id}/finance/`. Payments pick students through a search (`students/search/`) that also shows what each student owes. Money that is not a student fee (donations, canteen sales, rentals and so on) is recorded under Other income (`other-income/`, `income-categories/`), and the Money received report (`reports/money-received/`) combines fees and other income by cash, bank, cheque and mobile money, with date, method, source, class and status filters.

Finance campus access is fail-closed for accountants. Owners and school admins manage explicit grants in Finance Settings, or through `GET finance/campus-access/` and `PUT finance/campus-access/{membership_id}/` with a `campuses` array. Accountants without grants see no invoices or expenses. With grants, they may view and issue invoices, create, view and submit expenses, and view expense and outstanding-invoice reports for those campuses; unassigned records remain inaccessible to accountants. The Money received report includes only allocations to authorized invoice campuses, excluding advances, refunds, pending payments and other income; later allocation changes may change the report. Restricted outstanding reports use class names from invoice snapshots. Earlier balances on restricted invoice views and outstanding reports cover only granted campuses and may not represent the student's full balance. Other finance features, including general student payment workflows, expense payments, other reports, billing creation, adjustments, supplier operations and school-wide ledgers, remain unavailable to accountants until their campus scoping is implemented. Parent and student portal access to their own records is unchanged. Term-closure finance summaries are restricted to owners and admins.

Accountants can record cash, bank-transfer or cheque payments against one authorized outstanding invoice from its detail page. Each payment must be fully allocated to that invoice; advances and mobile-money confirmation remain administrator-only. `POST finance/invoices/{invoice_id}/payments/` requires an idempotency key and rejects amounts exceeding the invoice balance. Accountants can view a confirmed receipt only when all of its allocations are fully attributable to their granted campuses and no advance or refund is present. The general payment register remains restricted.

Finance migration `0007` adds the grant table without modifying existing financial records; it gives existing accountants no grants. Reversing it deletes all campus grants and must be coordinated with an application rollback: export grants first and do not run code expecting the table against the reversed schema. Deploying older code may restore broader accountant access, so assess that authorization change before rollback.

- **Setup:** configure invoice, receipt, and credit-note numbering; add ledger accounts and payment methods; create, close, and reopen accounting periods. The currency is currently fixed to GHS.
- **Accounting:** manage a tenant-scoped chart of accounts, preview a CSV (`account_code,debit,credit`, optional `description`) or enter balanced opening balances for approval before posting, inspect the posted journal register and general ledger, and view a trial balance. Posted entries are immutable; corrections use reversing entries.
- **Supplier payables:** maintain suppliers and school-configured purchase-tax codes, record multi-line supplier bills with campus cost-centre allocations, calculate configured inclusive or exclusive line tax, securely upload/download private PDF/PNG/JPEG bill documents, post bills to accounts payable, prepare and approve payment vouchers, record bill allocations or supplier advances, reverse posted transactions, and review supplier statements and ageing.
- **Supplier opening balances:** allocate suppliers' debit/credit detail against an already-posted accounts-payable opening import without creating duplicate journal entries. The payables page compares the accounts-payable control account with supplier and expense subledger balances and displays any difference.
- **Direct expenses:** submit expenses for approval, post approved expenses to accounts payable, record full or partial payments from a selected asset account, and review expense reports.
- **Fees and billing:** create academic years, fee categories and schedules, discounts, scholarships, exemptions, optional services, per-unit usage, invoice previews, bulk draft invoices, and batch issue.
- **Collections:** record staff-entered payments, confirm mobile-money receipts after external verification, allocate advances, create receipts/PDFs, and manage reversals, refunds, and credit notes.
- **Reports:** dashboard collections, outstanding and overdue balances, student advances, statements, ledger transactions, a trial balance, supplier payables ageing, expense reports, and account-level ledger activity.
- **Legacy attribution review:** owners and school administrators can open `reports/legacy-attribution-reconciliation/` to review missing invoice class/campus snapshots, tenant/reference mismatches, and confirmed payments with unallocated amounts or inconsistent allocation records. This paginated report is read-only. Current student details are comparison context only; it never guesses historical attribution or applies corrections.
- **Reminders:** review overdue students and whether guardian phone numbers are available. No SMS/WhatsApp provider is configured, so reminders are not sent.

Online checkout and automatic payment-provider callbacks are not enabled. Payments are recorded by staff, and mobile-money payments remain pending until an authorized finance user confirms them. Provider integrations require selecting a provider and configuring its credentials and webhook verification before they can be enabled.

Bill attachment storage uses private local media files by default and is suitable only for development or self-hosted deployments with protected, persistent storage. Set `DJANGO_MEDIA_ROOT` to a protected filesystem location; do not expose that directory as a public static/media URL. Production deployments should configure private object storage and backups before enabling financial uploads. Tax rates and posting accounts are entered by school admins; no jurisdictional statutory rates are assumed. Opening-balance CSV preview checks the school chart of accounts and debit/credit balance but does not create or post an import until a finance user reviews the lines.

The backend reads `backend/.env` and now accepts Django's standard `EMAIL_*` variable names as well as the earlier `DJANGO_EMAIL_*` aliases. Gmail SMTP on port 587 uses `EMAIL_USE_TLS=True` and `EMAIL_USE_SSL=False`; port 465 uses SSL instead, and both must not be enabled together. Store a Google App Password in `EMAIL_HOST_PASSWORD`, never a regular Gmail password. `EMAIL_HOST_USER` should be the sending Gmail account and `DEFAULT_FROM_EMAIL` a permitted sender address. Set `NLSCHOOL_FRONTEND_URL` to the frontend origin so emailed account links open the correct application; it is also the default allowed CORS origin. Set `CORS_ALLOWED_ORIGINS` to a comma-separated list if more than one frontend origin is required. SMTP connection/authentication was tested successfully; no email was sent as a test. In debug mode, the console backend remains the default only when no email backend is explicitly configured.

### Production configuration and release checklist

The application has production-mode configuration and deployment checks, but that is not a certification of a specific live deployment. A real release still needs an operator to verify the target database, TLS termination, private file storage, backups, email delivery, and restore procedure.

Set `DJANGO_ENV=production` and configure these environment variables through the deployment platform's secret manager (do not commit them):

- `DJANGO_SECRET_KEY` (at least 50 characters), `DJANGO_DEBUG=false`, and `DJANGO_ALLOWED_HOSTS` (comma-separated API hostnames; no wildcard or local development hosts).
- `DJANGO_DB_ENGINE=django.db.backends.postgresql`, `DJANGO_DB_NAME`, `DJANGO_DB_USER`, `DJANGO_DB_PASSWORD`, and `DJANGO_DB_HOST`. PostgreSQL connections use TLS with `DJANGO_DB_SSLMODE=verify-full` by default; `verify-ca` is also accepted. Configure the database CA certificate where required by the provider.
- `NLSCHOOL_FRONTEND_URL` (one HTTPS origin), plus `CORS_ALLOWED_ORIGINS` and `CSRF_TRUSTED_ORIGINS` when additional HTTPS frontend origins are needed.
- `EMAIL_HOST`, `EMAIL_PORT`, `EMAIL_USE_TLS` or `EMAIL_USE_SSL` (never both), `EMAIL_HOST_USER`, `EMAIL_HOST_PASSWORD`, and `DEFAULT_FROM_EMAIL` for authenticated SMTP.
- `DJANGO_MEDIA_ROOT` as an absolute directory outside the application tree. It must be persistent, private to the application, backed up, and not served directly by the web server. The current storage backend is local filesystem storage, so single-node storage is not automatically suitable for a multi-instance deployment.
- `NLSCHOOL_SETUP_TOKEN` only if the one-time initial school setup flow is still needed. Keep it secret; the endpoint becomes unavailable after initial setup.

Terminate HTTPS at a trusted reverse proxy/load balancer. Set `DJANGO_SECURE_PROXY_SSL_HEADER=HTTP_X_FORWARDED_PROTO` only when that proxy removes any client-supplied forwarded-protocol header and sets the trusted value itself. Do not enable `DJANGO_SECURE_HSTS_INCLUDE_SUBDOMAINS` unless every subdomain is HTTPS-only; HSTS preload is intentionally disabled and requires a separate domain-wide eligibility review.

For each release, use a single deployment job to take and verify a database backup, apply migrations, collect static files, run deployment checks, and then start the application. From `backend/`:

```sh
python manage.py migrate --noinput
python manage.py collectstatic --noinput
python manage.py check --deploy
gunicorn config.wsgi:application --bind 0.0.0.0:8000 --workers 3 --access-logfile - --error-logfile -
```

Run migrations once per release, not concurrently from every application instance. The production static-file middleware is WhiteNoise. Confirm the application health endpoint and a finance workflow after release. Configure automated encrypted database and private-media backups outside the application host, define retention and access controls, and regularly rehearse restoring both into an isolated environment. A successful `check --deploy` or test suite does not replace these operational checks or a PostgreSQL-backed deployment smoke test.
